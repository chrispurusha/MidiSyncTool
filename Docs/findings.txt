2026-09-03  A CLOCK INPUT - AND A STALE BUNDLE THAT LOOKED LIKE A REGRESSION
--------------------------------------------------------------------------
THE FALSE ALARM FIRST, because it cost time and will recur otherwise. The three-way mode drop-down
came up in Ableton as the old two-state button, which reads as a regression and was not one. There
were TWO MidiSyncTool.vst3 on the machine, correctly formed and identically named:

    build/MidiSyncTool.vst3              13:54   current
    build/release-tmp/MidiSyncTool.vst3  13:11   the previous build

build/release-tmp is do-release's private derived-data path, and it was left behind after a release
build. VST3 SCANNING RECURSES, so a host whose search path includes the project's build directory
finds both and may load either - and the one it loaded presented an old build's GUI with nothing
whatever to say so. The installed system-wide copy was current the whole time; grepping the binary
for the mode strings is what settled it in seconds.

Fixed at the source: do-release now builds in a mktemp directory - which cannot be on any host's
search path - and removes it on exit through a trap set beside it, covering success, failure and
interruption alike. The staging directory joins that same trap rather than installing a second one
on EXIT, which would silently replace the first.

  ** A BUILD ARTEFACT WITH A PRODUCTION NAME MUST NOT BE LEFT INSIDE A DIRECTORY A HOST SCANS. **

THE CLOCK INPUT, which is the actual work. src/msClockIn.c plus MIDI source enumeration and a
listener in src/msMidi.c, behind a new kParamClockSource. It MEASURES ONLY - nothing steers the
generated clock from it, which is a separate feature and should not be built on an estimator whose
numbers nobody has read yet.

WHAT IT IS FOR: the standing question "how much better is our clock than Live's own?" has never had
a defensible answer, because the only reference was a drum machine's audio onsets - carrying the
device, the desk and the A/D on top of anything the wire did. Now Live's Sync and this can be
pointed at the same IAC port and both clocks timed by the same code against the same reference. The
wire measures at 0.013 ms; the audio path at 0.132 ms at best.

VERIFIED against synthetic clocks at an exact 130 BPM / 19.230769 ms:

    perfect clock            130.0001 BPM   jitter 0.00031 ms   192 fitted   0 gaps
    1 clock in 20 dropped    130.0000 BPM   jitter 0.00030 ms   192 fitted   0 gaps
    2 s dropout mid-stream   130.0001 BPM   jitter 0.00003 ms   192 fitted   1 gap
    after STOP               running=0, stops=1, window cleared

THE SECOND ROW IS THE ONE THAT MATTERS. Fitting against ordinal position instead of an assigned
SLOT would read 20 real periods per 19 arrivals - 130 x 19/20 = 123.5 BPM, a 6.5 BPM error from one
clock in twenty going missing. Assigning n = round(t / period) makes it invisible. That is the THIRD
place in this project the same omission would have bitten; monitor mode was the second, where a rest
in the drum pattern did it. The period itself comes from the MEDIAN interval for the same reason - a
mean carries one doubled interval into the rate for the whole window.

Live self-test through IAC, the plug-in measuring its own generated clock: 129.9966-130.0001 BPM,
jitter 0.025-0.044 ms RMS, 0 gaps. That agrees with the 0.033 ms measured a day earlier by
tools/midiTimestampTest.c - two independent code paths, one answer. The ppm column wanders +/-26 ppm
run to run, which is larger than the fit's own standard error (~3 ppm) and is the usleep harness's
pacing rather than the estimator; it should be re-read against a real host before being quoted.

A FIFTH PARAMETER COULD NOT SIMPLY EXTEND THE SAVED STATE, and this would have been a silent
corruption. The block is [4 doubles][64-byte destination name], so reading 5 doubles from an OLD
block succeeds, is not short, and loads the first eight characters of the port name - "IAC Driv" -
as a parameter value. Everything added after v1 therefore goes AFTER the name, where an old file
runs out and the short read leaves the default standing. The controller's setComponentState had to
learn the identical layout, or the two halves would disagree about what the plug-in is set to with
only the controller's version on screen.

The panel's heading over the control rows is now SETUP rather than MIDI OUTPUT: two of its five rows
are inputs, and it was already half wrong before the clock input made it plainly so.

2026-09-03  HOST BLOCK JITTER READ 89 ms BECAUSE ABLETON WENT TO THE BACKGROUND
--------------------------------------------------------------------------
Reported from a real session: "host block jitter seems much higher than it was", then "jitter now
seems OK on an Ableton restart", then the diagnosis - "possibly happened when I pulled the terminal
to the foreground". All three observations are the same bug.

THE METRIC HAD NO WAY TO FORGET, AND NOTHING CLEARED ITS BASELINE. blockPeriodRmsMs is
sqrt(sumPeriodErrSq / blockCount) over the whole run, and `havePrevBlock` was set true in one place
and cleared in NONE. So any interval in which the host stopped calling process() was measured as a
single colossal callback period and squared into a sum that never forgets. Backgrounding Ableton
does exactly that.

MEASURED, against msStats directly - a host that is otherwise PERFECT:

    5 min at exactly the nominal period          block period RMS  0.0000 ms
    + one 30 s gap, then 5 min more, perfect     block period RMS 89.4431 ms

Ninety milliseconds of reported host jitter, every bit of it the metric's own fault, and permanent
until the plug-in reloaded - which is precisely why restarting Ableton "fixed" it.

THIS IS THE SAME BUG AS THE MODEL RESIDUAL'S `haveBase`, in a second place, and the general rule is
now stated twice: WHENEVER A METRIC IS A STEP BETWEEN TWO SAMPLES, ASK WHAT CLEARS IT. A flag set in
one place and cleared in none is the signature.

Two fixes, because the two failure modes are different:
  - ms_stats_gap() drops only the previous block's timestamp, and setActive/setProcessing call it
    through MstProcessor::suspend(), which also clears clock.haveBase and clock.havePrev. That
    covers every suspension the HOST announces. No accumulated figure is discarded: a suspension is
    a reason not to measure the hole, not a reason to throw away the run.
  - MS_STATS_GAP_MS (250 ms) covers the ones it does not announce, which is the backgrounding case -
    the process simply stops being scheduled with no setProcessing(false) to say so. An interval
    beyond it is COUNTED, never summed.

The count is published and shown beside the figure ("0.212 ms RMS (2 gaps ignored)") rather than
swallowed. Without it the same reading means two different things - a steady host, or one that
stalled twice and had it quietly discounted - and a metric that silently drops its worst samples is
a prettier lie than one that keeps them.

Verified: the 30 s gap now costs 0.0000 ms and reads "gaps 1", while a genuinely late 40 ms block is
still measured and still reported as the worst case (RMS 0.1193, worst +40.000). The guard must not
swallow the thing it exists to report.

NOT A REGRESSION FROM THE MODE WORK, and that was checked rather than assumed: the same harness run
against a build of the previous commit and against the new one gave 0.546 / 0.593 ms and 0.572 /
0.574 ms - indistinguishable. msStats.c was not touched by that change at all.

AND THE ~0.55 ms IN THOSE RUNS IS NOT A PLUG-IN FIGURE. mstDriver --realtime without --audio is the
usleep harness, which reports its own overshoot; it has now misled this project three times. Any
block-jitter number quoted without --audio or without a real host is the harness measuring itself.

2026-09-03  A THIRD MODE - AND THE CPU ARGUMENT FOR IT WAS MEASURABLY WRONG
--------------------------------------------------------------------------
The Mode control is now a three-item drop-down (kParamMode, id 3) rather than a two-state Monitor
toggle: Generate + measure, Generate clock only, Monitor.

THE IDEA WAS "A CLOCK FILTER WITHOUT THE ANALYSIS, TO SAVE CPU". THE SAVING DOES NOT EXIST.
Benchmarked ms_detect_audio() on its own, 200000 blocks of 256 frames at 48 kHz, -O2:

    231 ms of CPU for 1067 s of audio  =  0.022 % of one core
    1.16 us per 256-frame block, against a block period of 5.333 ms

One high pass, one envelope, one floor follower and two comparisons per sample; monitor_fit()'s
least squares runs per ONSET, a handful of times a second. There is nothing to reclaim. Same shape
as the jitter budget of the same day: the term that looked worth optimising was a rounding error
against everything around it. Do not sell this mode as a CPU saving.

WHAT IT ACTUALLY FIXES IS A PANEL THAT LIES, and that defect is real and reproducible:

    mstDriver --realtime --seconds 10, silent input, clock into IAC, Generate + measure:
        hits 0  missed 17  spurious 0

Every 24th tick registers an expectation and ms_detect_audio() ages it out against silence, so a
plug-in on a track the drum machine does NOT come back on counts a miss per beat - about 7800 an
hour - and reads as a fault when nothing whatever is wrong. Once a device's latency is known, the
everyday use of this plug-in is as a clock on whatever track suits, and that is now a mode. Same
run in Generate clock only: 0 missed, 0 device lines logged, clock unaffected (313 ticks, 0 late,
commit margin +12.7 ms mean / +9.4 ms worst).

THE SAVED-STATE COMPATIBILITY IS FREE, AND ONLY BECAUSE OF THE ORDERING. The toggle wrote exactly
0.0 or 1.0 into values[3]; with Measure at step 0 and Monitor at step 2, those are this parameter's
first and last normalised values. Every set saved by the older build opens in the mode it was saved
in with no migration branch. A fourth mode must therefore be inserted in the MIDDLE, never at
either end.

THE FIGURES ARE PRESERVED WHEN THE DETECTOR GOES QUIET, and every other source change still clears
them (ms_detect_set_source). They are kept because the compensation dialled in on the panel came
out of them, and a value in force with no visible provenance is worse than a dim number. Verified
directly: after a run, -> eMsDetectOff preserved hits and mean, 400 further silent blocks added no
misses, and -> eMsDetectFromClock cleared.

A HELD FIGURE MUST NOT LOOK LIKE A LIVE ONE, and colour alone will not carry that. Four cues:
  - the section heading gains "- HELD FROM THE LAST RUN"
  - a line under it names the mode that would make it live again
  - both text tiers drop together (MS_HELD_CAPTION / MS_HELD_FIGURE, about 2:1 contrast)
  - the verdict loses its GREEN and gains "(held)" - it is the one thing on the panel a user reads
    without reading, and a green EXCELLENT over a measurement that stopped ten minutes ago is the
    worst single failure this panel could have

THE SWEEP FOR INACTIVE FIGURES FOUND TWO EXISTING ONES THAT WERE WORSE THAN STALE:
  - In monitor mode ms_clock_process() returns at the top with no destination and the stats are
    reset on the way in, so Commit margin and Late clocks read a PERFECT 0.00 ms / 0 - the panel's
    most reassuring possible reading, produced by sending nothing at all.
  - The LATENCY BREAKDOWN in monitor mode divided every term by lead + roundTrip with roundTrip at
    zero, so Schedule lead drew a full-width bar as 100 % of a "Total musical delay" of 10 ms that
    nothing on the rig was waiting. It is now NOT APPLICABLE there.
Host block jitter and Clock drift stay live in all three modes, and correctly so: ms_stats_block()
runs before the clock and unconditionally, and drift is audio seconds against wall seconds.

2026-09-02  CLOCK GENERATES CORRECTLY - AND NEEDS A LOOKAHEAD
------------------------------------------------------------
src/msClock.c generating 24 PPQN from the host's ppq, sent through src/msMidi.c with a scheduled
timestamp, driven offline by tools/mstDriver at 130 BPM with a 1-bar loop.

CORRECT, on the musical side:
  - 419 ticks in 8 s = 52.4/s, and 130 BPM x 24 PPQN is 52.0 - right rate, right tempo.
  - The wrap counter increments exactly once per loop, so the correction in ms_clock_process() is
    firing on Live's snap-to-loop-start pattern rather than being fooled by it.
  - Tempest appears in the destination list (index 7 here), so the intended first target is
    reachable without any further work.

NOT YET GOOD ENOUGH, on delivery. Measured through IAC, target 19.2308 ms between ticks:
                                     mean         RMS        worst
  raw timestamp test (no plug-in)  -0.0003 ms   0.019 ms   +0.054 ms
  clock through the plug-in        -0.1307 ms   1.667 ms  -18.050 ms

  The mean is fine, so nothing is drifting. The RMS and that -18 ms worst case are BUNCHING: a tick
  is currently scheduled for "this block's wall time plus its offset within the block", so if a
  block is picked up late, some of its ticks are already in the past when they are submitted and
  CoreMIDI delivers them at once.

  THE FIX WAS NOT A LOOKAHEAD, though that was the first guess and it was wrong. Adding one changed
  nothing (1.667 -> 1.711 ms RMS), which is what sent the investigation somewhere better: printing
  WHERE the outliers fell rather than how big they were.

  They landed 96, 96, 96 ticks apart. 96 ticks is exactly one bar of 4/4 at 24 PPQN - so it was the
  LOOP WRAP every time, and structural rather than noise. The signature was a ~2 ms interval
  followed by a long one: a DOUBLED TICK. The tick at the loop END and the tick at the loop START
  are the same musical moment, and a generator that searches for every 1/24 boundary inside each
  block's musical span emits both.

  Replacing that search with a PHASE ACCUMULATOR fixed it. Carrying the leftover fraction of a tick
  from block to block cannot revisit a boundary, so it cannot duplicate one, wrap or no wrap:

                              mean         RMS        worst      outlier spacing
    range search           -0.131 ms   1.711 ms  -18.019 ms      96, 96, 96 (structural)
    phase accumulator      +0.002 ms   0.922 ms   -2.503 ms      54, 45 (scattered)

  Tick count came out at 519 against the 520 the tempo predicts, so nothing is being dropped either.

  THE LOOKAHEAD IS STILL THERE AND IS STILL UNJUSTIFIED. Swept at 5 / 10 / 30 ms it gave 0.936 /
  0.891 / 0.901 ms RMS - no effect at all. It is kept at 10 ms because the failure it guards against
  is real in principle and costs only a known constant, but nothing here has demonstrated it buys
  anything, and this harness may be incapable of showing it. Revisit against a real host under load.

  THE REMAINING 0.9 ms IS PROBABLY THE HARNESS, NOT THE PLUG-IN. The raw timestamp test, with no
  plug-in and no block pacing, reached 0.019 ms through the same port. The difference is that
  mstDriver paces blocks with usleep, so the blockHostTime every tick is placed against is itself
  jittering. That claim is untested; Live is the place to settle it.

TWO HARNESS BUGS FOUND BY THIS, BOTH MINE, both of which produced numbers that looked like plug-in
defects:
  1. --realtime slept one block's length per block. usleep always overshoots, so the harness ran 20%
     slow (wall +6.4 ms against 5.33), dragging every scheduled tick with it: a +3.27 ms MEAN error
     that was entirely the harness. Now sleeps until block N is DUE, against an absolute start.
  2. The clock listener matched source names one way round only. IAC's destination is "IAC Driver
     Bus 1" and its source is just "Bus 1", so it connected to nothing and reported no measurement -
     which reads as "the clock never arrived".

Worth keeping in mind for everything that follows: this harness is a sleeping loop pretending to be
an audio callback, and its own timing is nowhere near a real host's. Delivery figures from it are
indicative. The number that counts comes from Live.

2026-09-02  SCHEDULED MIDI IS 220x TIGHTER THAN IMMEDIATE - MEASURED
------------------------------------------------------------
tools/midiTimestampTest.c. 200 clock bytes at 20.8333 ms apart (24 PPQN at 120 BPM) down IAC Driver
Bus 1 and received on its own source, timed on arrival.

                          mean error      RMS        worst
  SCHEDULED ahead         -0.0003 ms   0.019 ms   +0.054 ms
  IMMEDIATE (ts 0)        +3.8703 ms   4.157 ms   +6.871 ms

CoreMIDI honours a future timestamp, and honours it well: 19 microseconds RMS with no systematic
drift. Sending with timestamp 0 from a sleeping loop - the shape of a generator that emits at block
boundaries instead of scheduling - is 220 times worse on RMS AND carries a 3.9 ms MEAN error,
because a sleep always overshoots and the error accumulates rather than averaging out.

So the design decision is settled with a number rather than an argument: hand CoreMIDI the future
time and let the driver place it.

A TRAP ON THE WAY, worth recording because the first result was a lie. The receive callback
originally recorded the PACKET'S OWN timestamp, which IAC passes through untouched - so it measured
whether CoreMIDI can copy a number back, and duly reported RMS 0.0000 ms. A perfect result that
flattered the design and meant nothing. The arrival time has to be read from the wall clock in the
callback. Any future measurement through a virtual port needs the same care.

CAVEAT: IAC is an in-memory virtual driver. A real DIN interface adds its own jitter, and the wire
itself is about 320 microseconds per byte at 31250 baud - so the interface will dominate in
practice. What this establishes is that OUR contribution sits far below anything we would be trying
to measure in someone else's equipment.


2026-09-02  A HOST THAT LIES THE WAY ABLETON LIES
------------------------------------------------------------
tools/mstDriver - a headless VST3 host that hands the plug-in a ProcessContext modelled on the
measured behaviour of Live 12.4.5, so clock work can be developed and regression-tested without a
DAW and without CT in front of one.

DELIBERATELY NOT A CORRECT HOST. An idealised one would be worse than useless: it would let a
scheduler be written against continuous musical time, which is the exact assumption Live breaks. So
it reproduces the faults:
  - systemTime always 0 and kSystemTimeValid never set, whatever the plug-in asks for
  - continousTimeSamples always 0
  - the block is never split at a loop boundary
  - AT A WRAP the report LAGS BY ONE BLOCK: the block after the wrap reads exactly the loop start,
    and the one after that reads the remainder the wrap actually left - not remainder-plus-a-block

That last point took two attempts. The first version advanced the position through the snap block,
which put the harness a whole block ahead of Live - and a scheduler developed against it would have
come out systematically early by up to 5.3 ms at 130 BPM, which is precisely the class of defect
this tool is meant to detect in other people's equipment.

VERIFIED AGAINST THE CAPTURE, 130 BPM, 1-bar loop, 256-frame blocks at 48 kHz:

                        Live (measured)          mstDriver
  block before wrap     ppq 3.998222             ppq 3.998222
  snap block            0.000000, smp 0          0.000000, smp 0
  block after           0.009750, smp 216        0.009778, smp 217
  second wrap           3.996417 -> 0 ->         3.996444 -> 0 ->
                        0.007944, smp 176        0.008000, smp 177

Within one sample throughout, and it reproduces the drift between successive wraps (3.998, 3.996,
3.994) that comes of a loop length which is not a whole number of blocks.

WHAT IT DOES NOT MODEL YET: tempo ramps (Live reports tempo per block and ppq stays continuous
across a change - worth adding when the estimator is written), transport start/stop, playhead jumps
while stopped, and buffer size changes.


2026-09-02  WHAT LIVE DOES AT A LOOP WRAP - AND WHY IT MATTERS
------------------------------------------------------------
Second capture, with a 1-bar loop at 130 BPM and tempo changes, after a reload. 35 discontinuities.

THE BLOCK IS NEVER SPLIT. n=256 on every single line, wrap or no wrap. Live does not hand a short
block at the loop boundary, so a wrap always falls INSIDE a block. That was worth checking, because
if it had split, a tick scheduler could have treated every block as musically contiguous.

WHAT ACTUALLY HAPPENS, and it is not continuous:

    JUMP  ppq 3.998222 -> 0.000000  (expected 4.007972)  smp 0
    JUMP  ppq 0.000000 -> 0.009750  (expected 0.011556)  smp 216

  At 130 BPM a quarter note is 22153.8 samples and a 256-frame block is 0.011556 QN - which is
  exactly what the prediction says, so the arithmetic is sound. Then:
    - the block starting at 3.998222 would have ended at 4.009778, i.e. 39.4 samples PAST the loop
      end at 4.0
    - the next block reports ppq EXACTLY 0.000000 and projectTimeSamples EXACTLY 0
    - the block after that reports 0.009750 QN / 216 samples - and 256 - 39.4 = 216.6

  So Live reports one block AT the loop start regardless of where inside the block the wrap actually
  fell, and the true sub-block phase only shows up in the FOLLOWING block. projectTimeSamples snaps
  the same way, so the two agree with each other and both lie in the same way.

  THE CONSEQUENCE FOR THE SCHEDULER: the exact sample at which the loop wrapped CANNOT be read from
  projectTimeMusic. It has to be inferred - (previous ppq + one block) minus the loop end, converted
  to samples. Assuming continuity across a wrap would put every tick after it out by up to a block,
  which at 130 BPM is 5.3 ms, and it would be a systematic error rather than jitter.

OUR OWN CLOCK WORKS. With systemTime unavailable (see the previous entry), AudioGetCurrentHostTime()
read at the top of process() advances by "wall +5.33 ms" line after line - 256/48000 is 5.333 ms
exactly. Steady enough to schedule against, which is the thing that had to be true for the
replacement plan to stand up.

TEMPO CHANGES are reported per block and ppq stays continuous across them (105 -> 114 -> 117 -> 118
in one capture). The small JUMP lines with deltas around 1e-4 are tempo ramps, not discontinuities:
the prediction uses the previous block's tempo and the tempo moved. The 1e-6 tolerance is too tight
and turns a ramp into twenty log lines - it should scale with a fraction of a block.

kCycleActive appears as CYCLE in the flags whenever loop is enabled, so the plug-in can tell that a
wrap is even possible before one happens.


2026-09-02  WHAT ABLETON ACTUALLY GIVES US - AND WHAT IT DOES NOT
------------------------------------------------------------
First plug-in, loaded on an audio track in Live 12.4.5 at 105 BPM, 4/4, 48 kHz, 256-frame blocks.
49 logged lines covering stopped, playing, a playhead jump and stopped again.

WORKS, and the design depends on all of it:
  - processContext is NOT null. IProcessContextRequirements did its job; asking for it on the first
    commit was the right call and a plug-in that skipped it would have got nothing.
  - kTempoValid, kProjectTimeMusicValid, kBarPositionValid, kTimeSigValid and the transport state
    are all set, every block.
  - tempo and ppq are EXACTLY self-consistent. At 105 BPM the heartbeat two seconds apart advances
    ppq by 3.5000 every time - 105/60 * 2 = 3.5 quarter notes. No rounding drift over the capture.
  - projectTimeSamples is exact and matches: ppq 3.5 at sample 96000, which is 2.0 s at 48 kHz.
  - barPositionMusic is the ppq of the current bar's start (144.0 when ppq is 146.0, i.e. bar 37 of
    4/4). Useful directly for Song Position Pointer.

DOES NOT WORK, AND IT IS THE ONE THE WHOLE SCHEDULING PLAN RESTED ON:

  *** ProcessContext.systemTime IS ALWAYS ZERO, AND kSystemTimeValid IS NEVER SET. ***

  All 49 lines: "sysTime 0", and the flag list reads "tempo ptMusic bar timeSig" with no sysTime -
  despite kNeedSystemTime being requested. continousTimeSamples is likewise always 0.

  design.md said: read systemTime, convert with AudioConvertNanosToHostTime(), hand CoreMIDI packets
  stamped in the future. That is not available. The replacement is to call AudioGetCurrentHostTime()
  OURSELVES at the top of process() - which gives the wall clock at the moment the block is being
  computed, NOT the moment its audio will be heard. The difference is the output latency: unknown,
  but CONSTANT for a given device and buffer size.

  So the architecture survives and one thing changes character: the round-trip measurement stops
  being a nicety for section 4 and becomes LOAD-BEARING, because it is what turns "now, as the CPU
  sees it" into "now, as the listener hears it". Everything else - ppq, tempo, sample position - is
  solid enough to schedule against once that constant is known.

STILL UNKNOWN: what a LOOP WRAP looks like. The capture contains one big discontinuity (ppq 10.5 ->
146.0 between two heartbeats) from a playhead move, but the 2-second heartbeat is far too coarse to
show what Live does at a loop boundary - which CT flags as the tricky part. The logging needs to
fire ON DISCONTINUITY, not on a timer, before that question can be answered.

2026-09-02  THE 0.92 ms JITTER WAS THE HARNESS, ENTIRELY - measured, not argued
------------------------------------------------------------------------------
mstDriver paced its blocks with usleep against an absolute deadline. That fixed the 20% drag but
not the per-block scatter, and the scatter went straight into blockHostTime, from which every tick
is stamped. The suspicion was recorded in to-test.txt as "probably mostly harness". It was all of it.

The same plug-in, same IAC destination, same 130 BPM, same 24 PPQN, differing only in what paced
the blocks:

                              block period RMS      delivered interval RMS      worst
  usleep loop, 256 frames         1.05 ms                0.97 ms             -2.53 ms
  QU-24 callback, 512 frames      0.019 ms               0.033 ms            -0.14 ms

A factor of 30. The raw timestamp test in tools/midiTimestampTest.c had already shown 0.019 ms with
no block pacing at all, so 0.033 ms from a real device callback is essentially that number plus the
device's own callback scatter - the generator is not adding anything measurable.

The lesson generalises past this project: a harness that paces with usleep cannot measure anything
finer than usleep's overshoot, and it will attribute its own overshoot to whatever it is testing.
Twice now that has produced a figure that looked like a defect in the plug-in - first a +3.27 ms
mean, now a 0.92 ms RMS - and both times the plug-in was innocent.

COMMIT MARGIN, the number that replaces the guessing about MS_LOOKAHEAD_MS. The plug-in now measures
how much future was left on each tick at the moment it was handed to CoreMIDI (msStats.c). Against
the QU-24 at a 512-frame buffer: mean +15.3 ms, minimum +10.04 ms, 0 late out of 332. The minimum
sits exactly at the 10 ms lookahead, which says the block was never late enough to eat into it. So
offline, on an idle machine, the lookahead is still unjustified - but the instrument to justify or
retire it now exists and reports from inside a real host under real load, which the offline sweep
never could.

DRIFT MUST BE COUNTED FROM THE TICKS, NOT FROM projectTimeMusic. The first version of the telemetry
divided reported musical position by wall time, and against a one-bar loop it reported 9.3 BPM
against a host tempo of 130 - because ppq goes backwards at every wrap. The tick count is monotonic
by construction and is also the thing actually being put on the wire.

THE HARNESS NOW RUNS REAL AUDIO. mstDriver --audio NAME opens a CoreAudio device (GenBridge's
device.c and ring.c, copied verbatim into src/ as msDevice/msRing), takes the plug-in's input from
--in-ch and writes its output to --out-ch. This is what section 3 of the concept needs: the plug-in
is an Fx precisely so it can hear the hardware answer its own clock, and none of that can be
developed against silence. Verified against the QU-24 on 2026-09-02: input from channel 14 (Tempest,
15/16 on the desk) read -62 dBFS of noise floor with the machine silent, 0 ring overflows and 0
underruns over 750 blocks.

TRANSPORT, verified offline. Start when play begins at zero; SPP followed by Continue when it begins
anywhere else - beat 128 for bar 8, MIDI beats being sixteenths; Stop on the falling edge, once. The
harness's listener prints them in arrival order, because an SPP that lands after its Continue is
useless and only the order shows that.

2026-09-02  TRANSIENT DETECTOR, and what its number does and does not contain
------------------------------------------------------------------------------
msDetect.c: one-pole high pass at 150 Hz, instant-attack envelope with a 15 ms release, a 400 ms
noise-floor follower, and an onset declared when the envelope clears the greater of 4x that floor
and -56 dBFS, with a 40 ms refractory. Each onset is matched to the OLDEST outstanding scheduled
tick within 300 ms - oldest rather than nearest, because a device whose latency approaches the
spacing between hits would otherwise match each transient to the NEXT hit and report a latency near
zero, which is both wrong and flattering.

VALIDATED WITHOUT HARDWARE. mstDriver --inject-ms D writes a click into the input buffer D ms after
every quarter note. The expected reading is D minus MS_LOOKAHEAD_MS, because the clock stamps a tick
10 ms ahead and that is genuinely when CoreMIDI puts it on the wire, so the latency is measured from
the stamp:

  --inject-ms 20, usleep pacing      mean 10.006 ms   jitter RMS 0.87 ms
  --inject-ms 20, QU-24 pacing       mean  9.997 ms   jitter RMS 0.038 ms

Against a prediction of exactly 10.000. The detector's own contribution to the jitter figure is
therefore about 38 microseconds, which is nothing against any drum machine - and once again the
0.87 ms was the sleeping harness rather than the code.

THE FIRST TICK NOW LANDS ON THE DOWNBEAT, at the same instant as the Start. Leaving phase at zero
put it one full tick later - 19.2 ms at 130 BPM. That is defensible by the standard and useless
here: gear differs on whether step 1 fires on the Start byte or on the first clock after it, and the
two readings would have differed by exactly that 19.2 ms with nothing to say which was right.

WHAT THE FIGURE CONTAINS. It is a ROUND TRIP: tick stamp, to transient in a buffer this plug-in was
handed. That includes the drum machine's MIDI-in to audio-out delay, which is the number worth
reporting, plus the interface's A/D, the host's input buffering and the lookahead. The extra terms
are constant for a rig and buffer size, so they are subtractable once measured - msDevice.c already
enumerates them. Until they are, the log says "round trip" and not "device latency". The JITTER
figure needs no such apology: every constant cancels in a deviation.

2026-09-02  FIRST REAL MEASUREMENT - Tempest over USB MIDI, audio via QU-24 15/16
------------------------------------------------------------------------------
NOTE PATH, the note probe with the Tempest's own sequencer idle. Forty notes, C1 (note 36 - that is
what Ableton calls C1, confirmed by the hardware answering it), velocity 110, 400 ms apart:

  round trip mean 21.94 ms, min 21.60, max 22.29, jitter RMS 0.162 ms, peak deviation 0.353 ms
  40 hits, 0 missed, 0 spurious - repeatable across runs to about 0.05 ms on the mean

That figure is a ROUND TRIP and contains the QU-24's A/D and a 512-frame input buffer (10.67 ms)
as well as the Tempest. The jitter figure contains none of that, because constants cancel.

CLOCK PATH: nothing. The Tempest receives Start and clock - the destination resolves, the transport
logs, the interval measures 0.033 ms RMS on the wire - and produces silence, 42 missed and an input
peak of -66 dBFS. It is not following external sync. Left with CT to check.

THE DETECTOR NEEDED THREE FIXES, and the first two were wrong repairs that the third replaced:

1. A time-only refractory. The kick was still sounding when the 40 ms gate lifted, giving exactly one
   spurious onset per hit at 40.0 to 46.3 ms - several at exactly the refractory, which is what said
   the envelope had never come down.
2. Hysteresis against the hit's own peak, plus freezing the noise floor during a hit so the drum
   could not raise its own bar. This moved the retrigger from 44 ms to 202 ms but did not remove it:
   captured and plotted, the kick has no second attack at all, just a long ripply tail hovering
   around the absolute floor for 300 ms and re-crossing it.
3. WHAT ACTUALLY WORKED: the detector only looks for a transient while one is DUE. This is a
   calibration instrument and it knows exactly when it expects a hit; outside those windows a rising
   edge is not a measurement of anything. 40 hits, 0 missed, 0 spurious, and no threshold anywhere
   was tuned to this drum, this desk or this gain - which the alternative repair would have been.

LATENCY COMPENSATION now exists: ms_midi_set_offset_ms(), applied inside ms_midi_send_at so it
reaches ticks, transport and probe notes alike and cannot put them out of step with each other.
Negative sends earlier. Proved against the harness's --echo-ms: a synthetic 7.5 ms device measured
7.58 ms and compensating by that figure brought it to 0.6 ms.

AND IT GIVES MS_LOOKAHEAD_MS ITS JUSTIFICATION AT LAST. An event cannot be sent earlier than the
block it was decided in, so the lookahead is the headroom the compensation spends - compensating
12 ms with 10 ms of lookahead cannot work, and the commit-margin telemetry says so by going
negative. The lookahead is not overhead, it is the budget.

TWO TOOLS THAT PAID FOR THEMSELVES IMMEDIATELY. tools/msLevels prints the peak on every input a
device has, which answered "is it arriving where you think" in five seconds - the question that cost
EmuUtility a whole session. tools/msCapture dumps one channel to raw floats, which is what settled
the 202 ms retrigger: the waveform showed there was no second hit, only a tail.

2026-09-02  THE CLOCK PATH, once the Tempest was actually slaved (its sync source was not USB)
------------------------------------------------------------------------------
  NOTE path  (probe C1, its sequencer idle)   mean 21.94 ms   jitter RMS 0.162 ms   40/40
  CLOCK path (its own sequencer, quarters)    mean 21.94 ms   jitter RMS 0.169 ms   42/42

IDENTICAL, to a thousandth of a millisecond on the mean. The difference between the two paths is
what the drum machine's own sequencer contributes, and on this machine it contributes NOTHING
measurable - its clock handling is as tight as its note handling. That is a real result about the
device, and it is only available because the two paths are measured separately.

Both figures are round trips and both contain the QU-24's A/D and a 512-frame input buffer.

COMPENSATION IS A PHASE ADVANCE, NOT AN EARLIER SEND. The obvious mechanism - subtract the measured
latency from each timestamp - cannot work, and the reason is arithmetic rather than tuning. A tick
for musical moment m is stamped at wall(m) + L and sounds at wall(m) + L + D, so landing it on m
needs the stamp at wall(m) - D: earlier than the block that decided it. Raising L raises the
requirement by exactly as much.

Measured, rather than argued. MST_OFFSET_MS=-21.9 against a 10 ms lead pinned every tick to the
present and took jitter from 0.169 ms RMS to 3.220 - it turned a clean clock into a bunched one,
which is precisely the defect this tool exists to remove.

The mechanism that works costs nothing, because the tick stream is periodic: a grid shifted earlier
by L + D is indistinguishable from one whose PHASE is advanced by that much, and phase is free to
move. Applied on hardware at 21.9 ms, the commit margin was unchanged (min +10.038 ms, 0 late of
832) and the clock stayed at 0.188 ms RMS. The advance is tracked incrementally rather than
reapplied, because it is a fixed number of milliseconds and therefore a changing number of quarter
notes - a tempo change must move the phase by the difference only.

The one casualty is the first L + D of a run: the grid cannot be advanced before the transport has
started, so the opening beat is uncompensated. Every beat after it is exact.

NOT YET VERIFIED END TO END. The measured round trip is unaffected by compensation, correctly - the
detector times from the stamp, so it keeps reporting the device's latency whatever is being done
about it. Proving the sound now lands ON the beat needs an independent reference: the host's own
audio. Patching QU-24 output 29 back to an input would supply it, and would pin the constant part of
the 21.94 ms at the same time.

2026-09-02  THE PANEL
------------------------------------------------------------------------------
Built on GenBridge's editor, which is now the house pattern for a plug-in panel: SynthLib's renderer
rather than AppKit widgets (so it cannot drift from the applications' look without the change being
visible in all of them), a Metal-backed NSView on a 30 Hz timer, and an IPlugView wrapper that is the
only Objective-C++ in the project.

WHAT IS SHOWN, in four sections: MASTER (host tempo, transport, position), MIDI OUTPUT (port, clocks
sent, commit margin and its worst case, late clocks, host block jitter), MEASURED DEVICE (round trip
mean/min/max, jitter RMS, peak deviation, detection counts, drift), and LATENCY BREAKDOWN. Then a
one-word verdict and a scrolling trace.

THE BREAKDOWN IS THE PART WORTH GETTING RIGHT, and the rule it follows is that a term is drawn only
if it is known:

  Schedule lead          exact, ours - MS_LOOKAHEAD_MS
  Audio input path       NOT knowable from inside a plug-in. The host owns the input device, and
                         VST3 tells a plug-in nothing about its latency. Drawn as "not measured"
                         with an empty bar until an audio loopback supplies it.
  Device MIDI to audio   what is left of the measured round trip once the above is taken out - and
                         while the input path is unknown it is labelled "Device + input path"
                         rather than "Device", because a figure called device latency that silently
                         contains an interface is exactly the overclaim this panel exists to avoid

Zero and "not measured" are different statements, and a panel that renders them the same way is
lying by omission. The bars make the dominant term obvious at a glance, which is the whole reason
for showing a breakdown rather than one number.

The trace is DEVIATION from the mean, not absolute latency: the absolute figure is a constant tens
of milliseconds tall and would flatten everything interesting into a straight line. One point per
detection rather than per block, since it is a picture of what the hardware did.

THE PROCESSOR-TO-EDITOR CHANNEL is GenBridge's status-slot mechanism, ported for the same reason it
exists there: with two instances loaded, a single global would have every editor reading whichever
processor wrote last. The processor claims a slot, sends the number over IConnectionPoint, and the
figures are then read straight out of the shared structure - a message per frame per instance would
be a great deal of allocation on a UI timer for numbers that are only ever advisory.

mstDriver now implements a minimal IHostApplication, because an IMessage can only be made by the
host: a driver passing nullptr as the initialise() context never exercises that path at all, and the
first place it would be tried would otherwise be Ableton. Verified: "controller connected", "editor
view created", "controller: status slot 0".

Building the panel needed freetype, which was not built in this project's own SynthLib checkout -
the nested ThirdParty submodules had never been initialised here. Recipe unchanged, in
G2-Edit/Docs/Third Party build notes.txt.

2026-09-02  THE PANEL'S CONTROLS, and why the environment variables had to go
------------------------------------------------------------------------------
The plug-in loaded in Live, drew every figure correctly, and generated no clock at all. A HOST
LAUNCHED FROM THE DOCK INHERITS NO SHELL ENVIRONMENT, so every MST_* variable this was developed
against was empty inside it: MST_MIDI_DEST resolved to nothing, clock.destination stayed -1 and the
generator returned immediately. G2-Edit's plug-in notes record the identical trap with
$G2_VST3_PATCH, and this is the second time it has been paid for.

Three real VST3 parameters now: MIDI destination (a list), latency compensation (0-100 ms), and
which channel the detector analyses (left / right / left+right). The panel has a drop-down for the
two lists and a stepper for the compensation, drawn with SynthLib's contextMenu - which scrolls
itself once the list will not fit, so an unbounded port count is safe.

A LIST PARAMETER'S STEP COUNT IS FIXED AT REGISTRATION and cached by the host, so it cannot follow
how many ports the machine has. Slot count is MS_MIDI_MAX_DEST and only the number of slots pointing
at something real varies - GenBridge's lesson, taken rather than repeated.

THE PORT IS SAVED BY NAME, NOT BY INDEX, and that was not a precaution: it was measured. The Tempest
was destination index 6 with a Kronos and a Hydrasynth powered up and index 4 with them off. A
project storing the index would open a different instrument on a different day, silently. When the
saved name is absent the panel says "waiting for <name>" rather than falling back to nothing chosen -
the two are different states and rendering them alike is how a saved setup starts driving the wrong
port.

BUFFER SIZE IS REPORTED, NOT SETTABLE. A hosted plug-in does not own it. It is shown anyway because
it is the largest exactly-knowable part of the input path, and the breakdown now subtracts it before
naming the remainder.

THAT TERM WAS THEN CONFIRMED BY ACCIDENT. Two runs of the same rig differing only in the QU-24's
buffer:

  512 frames    round trip 21.90 ms
  256 frames    round trip 16.55 ms
  difference     5.35 ms, against a predicted 5.33

So the audio in a block really is captured one full buffer before the block arrives, and the "Host
buffer" row in the breakdown is exact rather than an estimate. What remains unseparated is the
interface's A/D and the device itself, which is why that row is labelled "Device + interface" until
a loopback splits them.

mstDriver gained a minimal IParameterChanges and --param ID VALUE, so the route that replaced the
environment variables is exercised offline rather than first tried in Live.

2026-09-02  DRIFT, MADE READABLE - and what it now actually measures
------------------------------------------------------------------------------
The figure jumped about too much to read, and the cause was quantisation rather than noise. It was
computed from the TICK COUNT, and ticks are integers about 19 ms apart: one tick either way across a
five-second window is some 3800 ppm.

Counted in FRAMES instead, which is the audio clock itself and has no such step. That also changes
what the number means, for the better and precisely: it is now the host's AUDIO CLOCK against the
SYSTEM CLOCK. Blocks arrive at the interface's sample rate while the timestamps this plug-in hands
CoreMIDI are mach time, so this is exactly the quantity that decides whether a generated clock stays
with the music over a long session. GenBridge measures the same quantity between two devices and
steers a ring on it.

Measured on the QU-24, stable to about 1 ppm across a 46-second run:

  -19.0, -18.9, -19.1, -20.0, -19.0, -19.8 ppm

So its sample clock runs about 19 ppm slow against the Mac's - an ordinary crystal offset, and the
first genuinely physical number this tool has produced about the interface rather than about itself.

TWO THINGS HAD TO BE FIXED BEFORE IT SETTLED.

A LONG WINDOW OR NOTHING. Below about 30 seconds the reading is dominated by whatever the scheduler
last did rather than by any drift, so the panel now shows the window filling - "measuring - 12 of
30 s" - instead of a number that swings. Showing a figure and hoping the user discounts it is not a
design.

AND THE ANCHOR BLOCK'S FRAMES MUST NOT BE COUNTED. The anchor's wall time is taken at the START of a
block, so counting the frames that block goes on to deliver puts one whole block of audio time
against no wall time at all. It showed as a drift decaying like 1/t - 158 ppm at 30 seconds, 138 at
34 - which is the signature of a fixed offset being amortised rather than of any real drift. One
256-frame block is 5.33 ms, and 5.33 ms over 30 s is 178 ppm, which is the size of what was seen.

THE PANEL WAS ALSO TOO SHORT FOR ITS OWN CONTENT: about 740 units of rows in a 600-unit canvas, so
the graph fell off the bottom of the window. The canvas is now 740 AND the graph is anchored to the
canvas bottom rather than to the running y - so a row added above it can crowd the layout but can
never push it off again. A collision is visible; a control drawn past the edge is not.

The telemetry log line was gated on ticks having been sent, which meant a run with no destination
chosen produced no telemetry at all - exactly the run someone diagnosing a silent plug-in would be
looking at. Gated on the window instead.

2026-09-02  HOST JITTER IS NOW FILTERED OUT, and it was not before
------------------------------------------------------------------------------
CT asked whether the 0.232 ms of host block jitter Live was showing was being compensated. It was
not: every tick was stamped from AudioGetCurrentHostTime() read at the top of process(), so a block
delivered late by d carried every tick in it d late. All of the host's jitter was going onto the
wire, and the panel was reporting the cause while doing nothing about it.

This is the failure the concept names in section 2 - "do not simply react to instantaneous arrival
times... estimate the underlying phase and rate and independently schedule the cleanest possible
output". It applies to the HOST'S OWN timing quite as much as to an incoming clock, which is not
obvious until someone asks.

THE MODEL. A line through musical time against the wall clock: an anchor (musical position, mach
time) and a rate. Each block is one observation; the model is nudged towards it with a PI
correction; the ticks are stamped from THE MODEL rather than from the observation. A late block
therefore moves the output by Kp of its error instead of by all of it.

The rate term is not redundant with knowing the tempo. Tempo says how many quarter notes a second of
AUDIO time holds; the stamps are mach time, and the two are different crystals - 19 ppm apart on this
rig, which is 190 microseconds over ten seconds. Steady, and exactly what a phase-only correction
would chase for ever.

Musical time for the model is accumulated here (runQn) rather than taken from the host's reported
position, which goes backwards at every loop wrap. A resync threshold of 30 ms separates a seek, a
tempo change taking effect or a dropout from jitter: those re-anchor outright and are counted, rather
than being filtered through - smoothing across one would drag the output over seconds of wrong time.

MEASURED, on the same 130 BPM clock into IAC:

  host pacing            block jitter     delivered clock, before     after
  usleep harness          0.378 ms RMS          0.970 ms RMS       0.034 ms RMS
  QU-24 callback          0.009 ms RMS          0.033 ms RMS       0.018 ms RMS

A factor of 28 on the deliberately jittery host, and it improves the clean one too. The usleep
harness, which has spent this whole project misattributing its own overshoot to the plug-in, turns
out to be the ideal adversary for this: a host that is genuinely bad at delivering blocks on time.

The panel shows the pair - "Host block jitter" and "after filtering" - because either number alone
says nothing. The raw one on its own looks like a fault nothing is addressing; the residual on its
own hides how much work is being done. Resyncs are shown beside the residual when there are any,
since a residual that looks good because the model keeps re-anchoring is not a good residual.

2026-09-03  THE JITTER BUDGET, MEASURED END TO END - AND WHY THE WIRE IS FINISHED
════════════════════════════════════════════════════════════════════════════════════════════════════

Prompted by an observation from the panel in Live: the residual was reading AS BAD AS the raw host
block jitter, which would mean the timebase model was doing nothing. It was not. The model was fine
and the METRIC was lying, in two separate ways, both of them the same mistake.

*** THE RESIDUAL WAS CONTAMINATED BY ITS OWN RE-ANCHORS. ***

The residual is the step from one block's modelled base to the next, minus the nominal block
duration. Work that through the model's own update and it comes out at exactly MS_MODEL_KP times the
block's error - one PER CENT of the host's jitter at Kp 0.01. It can NEVER equal the raw figure. So
any run where it does is measuring something other than what it claims.

Two paths wrote a discontinuity into that step, and a sum of squares never forgets:

  - A RESYNC. predictedNs is forced to observedNs, so the step contains the whole re-anchor jump,
    worth up to MS_MODEL_RESYNC_MS. ONE resync in a thousand blocks is sqrt(30^2/1000) = 0.95 ms of
    pure artefact - four times Live's 0.232 ms raw block jitter, from a single sample.
  - THE FIRST BLOCK OF A RUN. The stopped path returns before the model runs, so lastBaseNs was left
    over from before the stop while `restarted` zeroed modelErrorSumSq and modelBlocks - but never
    haveBase. That block measured the entire STOPPED GAP as one residual sample. Seconds of it.
    It only bites on the second and later runs of a session, which is why it was not seen at once.

Fixed by dropping the base whenever it stops being continuous - haveBase = false on stop, on restart
and on resync. haveBase was set true in exactly one place and cleared in NONE; that was the whole
bug. modelWorstMs added alongside, because an RMS over thousands of blocks buries one bad block and
one bad block is a bunched pair of ticks.

MEASURED AFTER THE FIX, clock delivered into IAC and timed on arrival:

  host pacing            raw block jitter   residual        wire jitter
  QU-24 callback         0.008 ms RMS       0.0003 ms  4.3%  0.0134 - 0.0146 ms RMS
  usleep harness         0.847 ms RMS       0.009 ms   1.1%  0.0232 ms RMS

The 1.1 % against a genuinely bad host is Kp exactly, which is what says the loop is behaving as
designed rather than accidentally. Zero resyncs in every run.

*** THE RATE TERM WAS NEVER RUNNING UNDER TEMPO AUTOMATION. ***

Separately, and found by reading rather than by measuring: the tempo-change branch re-derived nsPerQn
from the new tempo, discarding the learned crystal ratio, and moved anchorQn to runQn. The rate term
estimates slope error as errorNs/span with span measured FROM THE ANCHOR and is gated on span > 1.0
quarter note - so moving the anchor set span back to one block, about 0.012 QN. A single tempo change
therefore stalled rate learning for half a second; a tempo RAMP, which reports a change on every
block, stalled it for ever and the model silently degraded to phase-only.

Fixed by holding the slope as a RATIO of the tempo's nominal ns-per-quarter (so the crystal part
survives a tempo change, a resync and a restart, while the tempo part is recomputed), and by
re-sloping through the current predicted point WITHOUT moving anchorQn.

HONESTLY, THE FIX COSTS MORE JITTER THAN IT SAVES, and the measurement says so. mstDriver gained
--ramp for this, ramping 120 -> 150 BPM across the run the way Live's tempo automation does. Three
runs each, usleep-paced, delivered into IAC:

  pre-fix (rate term dead)    0.0158 / 0.0160 / 0.0192 ms RMS
  post-fix (rate term live)   0.0221 / 0.0226 / 0.0227 ms RMS

Reproducible, not noise. The rate term injects about 0.006 ms by actively correcting; the pre-fix
build looked better precisely BECAUSE it was doing nothing, which is the same trap as a residual that
looks good because the model keeps re-anchoring. Sweeping the span gate at 1 / 4 / 16 QN moved it
not at all (0.0216 / 0.0217 / 0.0203), so the gate is not the mechanism.

KEPT ANYWAY, and the next section is why: 0.006 ms is invisible downstream. What it buys is the
standing phase offset a P-only loop cannot remove - rate error over Kp, which at 19 ppm and Kp 0.01
is about 10 us - plus not relearning the crystal from scratch after every restart and glitch.

*** THE BUDGET: THE WIRE IS 1 % OF IT, AND THE TOOL IS NOW MEASURING THE TRANSPORT ***

Tempest on USB MIDI, its own sequencer clocked by us, audio returning on QU-24 inputs 15/16:

  device | round trip mean 21.807 last 21.847 min 21.349 max 22.214 ms
         | jitter RMS 0.185 peak dev 0.458 ms | hits 78 missed 0 spurious 0

The 21.807 ms mean agrees with yesterday's 21.94 ms. The number that matters here is the 0.185 ms.

The detector's own precision was then isolated by injecting a click digitally - no analogue path at
all - PACED BY THE QU-24, which is the essential part:

  device | round trip mean 10.009 min 9.988 max 10.051 ms | jitter RMS 0.013 peak dev 0.041 ms

10.009 ms against an expected 10 (--inject-ms 20 less the 10 ms lookahead), so the detector is
correct as well as precise. NOTE the same run WITHOUT --audio reported 0.464 ms, which is the usleep
harness measuring its own overshoot again - see the standing warning about that harness. It is not a
detector figure and must not be quoted as one.

  stage                                     jitter RMS      share of total POWER
  plug-in -> CoreMIDI -> wire               0.015-0.023 ms  ~1.2 %
  onset detector + block quantisation       0.013 ms        ~0.5 %
  USB + Tempest + QU-24 A/D  (by quadrature subtraction)
                                            ~0.184 ms       ~98 %

SO: REMOVING THE WIRE'S CONTRIBUTION ENTIRELY WOULD TAKE 0.185 ms TO 0.1839 ms. The difference
between the pre-fix and post-fix builds moves the round trip by 0.0007 ms, against a peak deviation
of 0.458 ms. Further de-jittering of the generated clock is unobservable on this rig.

Worth noting where 0.184 ms probably comes from: a USB MIDI frame is 1 ms, and jitter uniform over
1 ms has an RMS of 1/sqrt(12) = 0.289 ms. The measured 0.184 is 0.64 of that, which is consistent
with USB framing being the dominant term. DIN is no escape - 31250 baud makes a single status byte
320 us - so ~0.2 ms is close to the floor of MIDI itself whichever transport is used. UNCONFIRMED as
a mechanism; the way to test it is the audio loopback below.

WHAT THIS MEANS FOR THE IDEAS THAT PROMPTED THE SESSION. Minimum-filtering the observation the way
NTP does (callback lateness is one-sided, so the least-late sample in a window is a better phase
estimate than the mean) and replacing the PI with a 2-state Kalman are both sound, and both would
reduce a term that is already 1/9th of the smallest thing downstream of it. NOT WORTH BUILDING until
something downstream gets an order of magnitude better.

STILL OPEN, and now the only way to push the 0.184 ms further apart: the audio loopback - QU-24
out 29 patched back to in 15 - which measures the interface's own D/A + A/D with no drum machine in
it. That is what would say how much of the 0.184 ms is USB and the Tempest and how much is the desk.

First run in Live with the model line, 130 BPM, 137 s:

  model | block jitter raw 0.228 ms -> residual 0.279 ms RMS (122.6 % of raw) worst 5.267 ms
        | 0 resync(s) over 25875 blocks
  timing| ... block period RMS 0.229 worst +5.209 ms ...

A residual ABOVE the raw figure is impossible for this filter - it works out to Kp times the block
error - so the metric was wrong again, in a second and unrelated way. The tell is the pair of worst
cases, 5.267 and 5.209 ms, agreeing with each other: 256 frames at 48 kHz is 5.33 ms. THAT IS A
BLOCK-SIZE CHANGE BEING REPORTED AS A TIMING ERROR.

*** BOTH PER-BLOCK FIGURES SUBTRACTED THE WRONG BLOCK'S NOMINAL DURATION. ***

The wall time between callback n-1 and callback n is the time the device took to consume block
n-1's samples. Both metrics subtracted block N's:

  msStats:  errMs = (t[n] - t[n-1]) - nominal[n]
  msClock:  runQn has not yet had this block's blockPpq added when predictedNs is computed, so the
            step from the last base to this one spans block n-1 - and it too subtracted nominal[n]

So each carried a term (nominal[n-1] - nominal[n]): the DIFFERENCE BETWEEN TWO CONSECUTIVE BLOCK
SIZES. With a fixed block size that is identically zero, which is why it survived every offline run
and every hardware run - a CoreAudio device hands over a constant block. Live varies it.

Both now compare against the previous block's duration, and blockFramesMin/Max/sizeChanges were
added to msStats with a "blocks |" log line that fires only when the host varies the size - because
every per-block figure here assumes it does not, and nothing previously said whether that held.

REPRODUCED OFFLINE with a new mstDriver --vary, which hands over 64..256 frames per call the way
Live splits its buffer. 30 s, delivered into IAC, same plug-in but for the two comparison lines:

  build                    raw block jitter   residual              wire
  off-by-one (as Live)     1.912 ms           1.667 ms  87.2 %      0.0226 ms RMS
  fixed                    0.492 ms           0.006 ms   1.2 %      0.0211 ms RMS

THE WIRE IS THE SAME IN BOTH, which is the whole point: the generated clock was never affected and
the ticks were always right. Note the RAW figure was inflated too, 1.912 -> 0.492, so both halves of
the pair were wrong together - which is exactly why the pair still looked plausible and why "show the
raw and the residual together" did not catch it. Constant-block runs are unchanged: QU-24 0.008 raw
/ 0.000 residual, usleep 0.311 raw / 0.004 residual (1.3 %).

LESSON, and it is the same one as the haveBase bug earlier today in a different disguise: a per-block
figure that assumes a constant block size must SAY SO, and must be checked against a host that varies
it. Two separate metrics had the identical fault, written at different times, because both inherited
the assumption silently.

2026-09-03  MONITOR MODE: MEASURING GEAR WE ARE NOT CLOCKING
────────────────────────────────────────────────────────────────────────────────────────────────────

A fourth detector source, eMsDetectMonitor, and a Mode toggle on the panel (kParamMonitor). Nothing
is sent at all - no ticks, no Start, no Stop - and the grid is recovered FROM THE AUDIO instead.

WHY IT IS NOT JUST "STOP SENDING". The other two sources measure a transient against a moment this
plug-in chose, which is the only way to get an absolute LATENCY and requires being the clock master.
Monitor mode gives that up and keeps the SPREAD, which is the audible part. Three steps:

  1. Estimate the hit PERIOD as the MEDIAN interval between onsets. Median, because a missing hit
     gives an interval of twice the period and one of those drags a mean badly.
  2. Assign each onset to a grid SLOT, n = round((t - t0) / period). WITHOUT THIS a pattern with any
     rest in it is fitted against a straight 0,1,2,3 counter, every slot after the rest is off by
     one, and the fit reports the resulting nonsense as jitter.
  3. Least squares for PHASE AND RATE TOGETHER, jitter = residual about that line.

THE RATE TERM IS NOT OPTIONAL. The host's grid and an external master's are unsynchronised
free-running crystals tens of ppm apart; over a hundred seconds they separate by milliseconds.
Fitting phase alone would report that separation as jitter and the figure would GROW WITH THE LENGTH
OF THE RUN. This is the same lesson as the timebase model's rate term, in a second place.

A SLIDING window of 256 onsets, not the whole run: a fit over everything since the transport started
slowly stops describing the present, and one tempo move would bias the residual for ever.

VALIDATED against a known-perfect grid - clicks injected digitally at one per quarter note, 130 BPM,
device-paced by the QU-24:

  monitor| grid 461.548 ms (129.997 BPM) | jitter RMS 0.017 peak dev 0.032 ms | 70 onset(s),
         | 0 empty slot(s)

461.5385 ms is the true quarter note at 130 BPM, so the fit is 0.010 ms out over 461 - TWENTY-TWO
PPM, which is the audio-clock-against-mach-time crystal difference this rig already measures at
-20 ppm. The fit is correct to the limit of the two clocks. The 0.017 ms jitter sits on the
detector's own 0.013 ms floor, so the fitting adds essentially nothing.

TWO BUGS FOUND BY TESTING IT, both worth recording:

  - THE CHOSEN PORT HAD NO OWNER. Monitor mode gates the destination to "none", and the first version
    recomputed the port from the PARAMETER when it did so - which silently discarded a port chosen
    by MST_MIDI_DEST at construction. Symptom: the harness set the port by name, toggled monitor
    mode, and the clock never came back, with the panel still naming the right destination. There is
    now one selectedPort, set by either route, and one place that gates it.
  - `running` SURVIVED A DESTINATION OF NONE. ms_clock_process returns early on a negative
    destination but left clock.running set, so leaving monitor mode mid-play would find restarted
    false and never send START or SPP - the device taking clock with no idea where in the bar it was.

*** THE MODE'S ONE REAL LIMITATION, and it is not a bug: MONITOR MODE STOPS A MASTER THAT IS SLAVED
TO US. *** Going silent is the whole point, and anything following our clock stops with us. The mode
is for a master running on its OWN timebase - a drum machine on internal clock, a hardware sequencer
in charge, a modular. Hit this immediately on first use: with the Cirklon in the chain, switching to
monitor produced silence on all 32 QU-24 inputs, because the Cirklon was still following Live.

2026-09-03  MONITOR MODE MEETS A REAL DRUM PART, AND A SINGLE GRID IS NOT ENOUGH
────────────────────────────────────────────────────────────────────────────────────────────────────

Monitor mode validated perfectly against injected clicks (461.548 ms recovered against a true
461.5385) and then reported 107 ms RMS against the Tempest playing an actual pattern. The device was
fine. The FIT was wrong, twice over.

FAULT 1 - the base period was the MEDIAN gap. That is right only for a calibration pattern where
every gap is the same. A real part has gaps of one and three subdivisions, the median is simply the
short gap, and the long gaps are then not whole multiples of it. Replaced with a low percentile as a
candidate plus a bounded search for the divisor leaving the least remainder across all gaps. That
found the right unit - 116.6 ms, matching the arithmetic - and the jitter only fell to 31 ms.

FAULT 2, and the real one - A SINGLE EVENLY-SPACED GRID CANNOT DESCRIBE A DRUM PART AT ALL. The
measured gaps alternate, dead stable:

  seq | 122.4 348.3 122.2 348.2 123.0 347.9 122.1 348.5 122.3 348.3 122.2 348.3 122.9 347.8

348.3 / 122.4 = 2.845. NOT A WHOLE NUMBER, so no uniform grid contains both gaps, and fitting one
reports the mismatch as jitter for ever. What is actually there is a PATTERN that repeats: k onsets,
then the same k again. Each position inside it may sit wherever it likes; jitter is how much a given
position moves FROM ONE REPEAT TO THE NEXT.

So the fit now finds the repeat length k (smallest k whose gap sequence matches itself k apart,
within 5 % of the mean gap) and gives EACH POSITION ITS OWN LINE - positions q, q+k, q+2k are evenly
spaced by one cycle whatever the pattern does inside it. Residuals pooled across positions.

  before (single grid)   jitter 31.1 ms RMS, base 116.6 ms, "514 BPM"
  after  (per position)  jitter 0.74 ms RMS, cycle 470.644 ms, 127.485 BPM, 2 hits per cycle

*** THE SHAPE IS NOW A MEASUREMENT IN ITS OWN RIGHT, and it is the figure an RMS destroys. ***

  shape | 2 hits per 470.645 ms cycle, at phases: 0.0000 0.7409

Straight sixteenths would put the second hit at 0.7500. It sits at 0.7409 - EARLY by 0.0091 of a
cycle, which is 4.3 ms - and it does so on every single repeat.

SHUFFLE WAS RULED OUT BY EXPERIMENT, not by argument. The displacement was first seen with the
Tempest's shuffle ON; the owner turned it off and predicted it would make no difference to sixteenths;
the displacement is still there, self-clocked, unchanged. The owner was right.

The remaining explanation is the one this file has warned about since the detector was written: ONSET
DETECTION IS BIASED BY ATTACK TIME. A kick's envelope ramps over milliseconds and a hat's does not,
so the threshold is crossed later on the kick. Two different drums in one pattern therefore sit at
two different apparent phases - and a 4.3 ms bias between a kick and a hat is entirely ordinary.
UNCONFIRMED as the mechanism; the velocity sweep already on the todo list, or simply programming the
same sound twice, would settle it in minutes.

THE JITTER FIGURE IS OUTLIER-DOMINATED AND SHOULD NOT YET BE QUOTED. 0.74 ms RMS against a peak
deviation of 7.94 ms says a handful of bad onsets, not a spread: two 8 ms outliers in 143 onsets are
alone worth 0.95 ms RMS. The raw gaps tell a much tighter story - the short ones span 122.1 to 123.0
and the long ones 347.6 to 348.6, so about 0.35 ms of interval scatter, implying roughly 0.25 ms of
phase jitter. Finding and rejecting those outliers is the next thing this mode needs.

AND THE COMPARISON THAT IS NOT YET AVAILABLE: 0.74 ms here against 0.113 ms for Cirklon-driven and
0.182 ms for USB-direct is NOT a like-for-like ranking. Those two are round-trip spreads measured
against OUR OWN tick grid; this is a residual about a line fitted to the data itself. Until the
outliers are dealt with and the same pattern is measured both ways, no statement about the Tempest's
internal clock against an external one is supportable.

2026-09-03  ABLETON SPLITS THE BLOCK AT A LOOP WRAP AFTER ALL - AT 512 FRAMES
------------------------------------------------------------
The 2026-09-02 entry above says "THE BLOCK IS NEVER SPLIT. n=256 on every single line, wrap or no
wrap." That is true and it is why this went unnoticed for a day: every capture behind it was taken
at a 256-frame buffer. AT 512 LIVE SPLITS, and it does it once every time round the loop.

CT's report: host block jitter jumps up every time the loop returns to the start, and the latency
breakdown's bars reset at the same moment. Both are the same fault and neither is in the host.

THE EVIDENCE, all of it from /tmp/midisynctool.log of that session (pid 12643), no new capture
needed:

  blocks | host block size VARIES: 8..512 frames, 883 change(s) over 53708 blocks

  - 53708 blocks at 512/48000 is 573 s; a 1-bar loop at 130 BPM is 1.846 s, so 310 loops.
  - 883 / 310 = 2.84 size changes per loop. One split is exactly three changes: 512 -> a -> b -> 512.
  - The same run at a 256-frame buffer (pid 7077) reported NO size changes at all.

  timing | ... block period RMS 0.625 worst -10.412 ms

  - The device cycle is 512/48000 = 10.667 ms.
  - 10.667 - 10.412 = 0.255 ms = 12.2 frames.
  - So the cycle went over as 500 frames and then 12. The two calls are microseconds apart because
    both are computed inside ONE audio callback, and ms_stats_block judged that ~0 wall gap against
    the first fragment's own 10.417 ms. -10.412 is that subtraction and nothing else.

WHY IT CLIMBED ALL SESSION. The block-period RMS is an all-time sum that never forgets - the same
property that made a single backgrounding read as 89 ms. A fabricated error every loop is a
fabricated error 310 times, and the figure walks up as the wrap's sub-block offset drifts (the loop
length is not a whole number of blocks, so the split point moves ~40 samples a loop and the fake
error grows towards a full cycle). Watching it "jump at the loop start" is watching exactly that.

WHY THE BARS RESET. status->blockMs is published from data.numSamples EVERY call, and the latency
breakdown's "Host buffer" term is built from it. On the two calls a wrap produces, the panel was
being told the host's buffer was 8 frames - 0.167 ms - so that bar collapsed, the remainder term
(roundTrip - known) jumped to absorb it, and the whole chart flickered once per loop.

THE FIX IS ONE TIMESTAMP, in msVst3.cpp's process(), not four special cases. A fragment's audio
begins where the frames already handed over this cycle end, so that - cycle start plus
framesSoFar/rate - is the moment handed to ms_stats_block, ms_clock_process, ms_probe_process and
ms_detect_audio. Across a whole cycle the corrected times still sum to the real interval, so a
genuinely late callback is still reported as one; within a cycle the fabricated error is exactly
zero. blockMs is published from the last COMPLETED cycle instead of the last call.

DETECTING A CONTINUATION took two attempts and the harness caught the first one.

  WRONG: "less than half the PREVIOUS CALL's own duration". Where the wrap falls early in a buffer
  the first fragment is small - 20 frames is 0.42 ms, half of it 0.21 ms - which is less than the
  work a host does between the two halves, so the split read as two cycles again.

  RIGHT: the frames must fit inside one buffer AND the call must share the cycle's wall instant
  (within half a buffer). The buffer is the LARGEST SINGLE CALL SEEN, deliberately not
  maxSamplesPerBlock: a host handing over 256 through a 512 declaration would put both thresholds
  exactly on a real cycle boundary, and measured behaviour cannot.

tools/mstDriver grew --split, which hands the cycle CONTAINING the wrap over as two back-to-back
calls. A clean run (15 s, 512 frames, 22 split calls) reports block period RMS 0.022 ms worst
-0.158 ms; with the correction disabled the same run shows multi-millisecond worst cases. The
harness's own usleep pacing is worth about 1 ms RMS on a busy machine, so it can demonstrate the
mechanism and cannot measure the improvement - Live is the reference, as ever.

NOTE FOR ANYTHING THAT READS THE PANEL: "Host block jitter" figures from before this build are not
comparable with figures after it, on any host that splits. A new row says so - it appears only when
splitting has actually happened, and gives the count.


2026-09-03  WHICH NUMBER SETS THE COMPENSATION - AND THE PANEL WAS SAYING THE WRONG ONE
------------------------------------------------------------
CT asked what to type into Compensation given what the panel shows. Four plausible figures were on
screen and three of them are wrong, which is a fault in the panel rather than a gap in the reading.

THE ANSWER: the DEVICE term - the breakdown's last bar, round trip minus the host buffer. Not the
round trip, and not the total. ms_clock_set_compensation_ms() has said so since it was written -
"Pass the DEVICE's round trip; the schedule lead is added here" - so the lead must not be included
either.

WHY THE ROUND TRIP IS NOT IT. msDetect.h:20 states what the figure is: stamp to the moment the
transient appeared in a buffer THIS PLUG-IN WAS HANDED. That is a loop, and the way back - the
host's input buffer and the interface's A/D - delays when the plug-in SEES the sound, not when the
sound exists. A phase advance is a change to when the device is played, so advancing by the return
path plays it early. At 512 frames the host buffer alone is 10.67 ms.

WHAT WAS WRONG ON THE PANEL:

  - "Total musical delay" showed lead + ROUND TRIP, and "Residual" showed total - compensation. So
    the panel's own arithmetic said: set compensation until Residual reads zero, i.e. to
    lead + round trip. That double-counts the lead (the clock adds it again) AND cancels the return
    path - about 20 ms early at 512 frames.
  - The one hardware application on record (findings 2026-09-02) used 21.9 ms, the full measured
    round trip, on a rig the same entry describes as containing the QU-24's A/D and a 512-frame
    input buffer. That entry says NOT YET VERIFIED END TO END, which is consistent: the run proved
    the phase advance did not wreck the jitter, not that the sound landed on the beat.

NOW: "Musical delay" = lead + device, shown as its two parts. "Compensation" shows the setting AND
the advance it produces (setting + lead), because those are not the same number and the difference
is not the reader's to remember. "Residual" = device - compensation, which the lead cancels out of.

AND A BUTTON, because a caption explaining the choice to every reader for ever is worse than getting
it right once: "Use measured" on the Compensation row applies the device term through the parameter,
so the host's automation and saved state see it like any other edit. Live whenever there is a
measurement behind it, INCLUDING when the figures are held - measure, switch to Clock only, apply is
the actual workflow.

STILL NOT HONEST, and labelled as such: the device term is round trip minus the host buffer only,
because inputPathMs is zero until an audio loopback measures the converter. So the button
over-compensates by the A/D. The bar is called "Device + interface" for that reason and becomes
"Device MIDI to audio" the moment the loopback fills the term in.

WORTH NOTING THE ORDER OF EVENTS: this figure was ALSO wrong for a second reason until this morning.
"known" subtracts blockMs, and blockMs was being published from the last process() call - which at a
loop boundary was a split fragment. The device term jumped every time round the loop along with the
bars. Both are fixed; the split fix had to land first for this one to mean anything.

OPEN, and now on the todo: ms_clock_set_compensation_ms's advance is gated on compensationMs != 0.0.
With compensation off nothing cancels the lead, so the whole grid goes out MS_LOOKAHEAD_MS late; and
setting X then returning to 0 mid-run skips the branch, leaving the old advance folded into the
phase until the next transport start. Not fixed here because it changes what every compensation
figure recorded so far means, which is CT's call.
