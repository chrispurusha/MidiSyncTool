- THE "USE MEASURED" BUTTON (2026-09-03), on the Compensation row of the LATENCY BREAKDOWN. Measure
  a device in Generate + measure, switch to Clock only so the figures go HELD, and press it: the
  Compensation row should take the DEVICE term - the breakdown's last bar - and the Residual row
  should drop to +0.00. Live's own generic parameter panel should show the same value, since the
  button goes through the parameter rather than round the host's back. It must stay clickable while
  the figures are held; that is the workflow it exists for.
- THAT THE BUTTON'S VALUE IS THE RIGHT ONE, which no click can prove: it is the round trip MINUS the
  host buffer, and it still contains the interface's A/D because inputPathMs is zero until an audio
  loopback measures it. So it over-compensates by the converter, sub-millisecond to a couple of ms.
  The end-to-end check is still the one findings 2026-09-02 asks for - the host's own audio as a
  reference, QU-24 out 29 patched back to an input.
- THE ROWS AROUND IT, which changed meaning: "Total musical delay" (lead + round trip) is now
  "Musical delay" (lead + device) and Residual is now device - compensation rather than
  total - compensation. Check by eye that the compensation row's value does not run under the
  button at x 372, at a compensation of 100.0 ms which is the longest it gets.

- THE SPLIT-BLOCK FIX AT A LOOP BOUNDARY (2026-09-03), and the reading that settles it. Set a 512
  frame buffer, loop a bar, play for a few minutes and watch "Host block jitter". THE NUMBER TO
  READ IS THE WORST CASE BESIDE THE RMS, not the RMS: before the fix it walked up towards a whole
  buffer (measured -10.412 ms against a 10.667 ms cycle) and jumped every time round the loop;
  it should now stay at whatever the host's real worst block is, around a millisecond, and NOT
  step at the wrap. A "host split blocks" row should appear under it with a non-zero count - if it
  stays absent the correction is not firing and the run proves nothing.
- THE LATENCY BARS ACROSS A LOOP, same run: the breakdown's Host buffer bar should now hold still
  at the wrap. It was being told the buffer was 8 frames on the two calls a split produces.
- THE SAME AT 256 FRAMES, which is the control: Live does not split there, so the split count must
  stay at zero and every figure must read as it did before this change.
- THE PANEL'S NEW SHAPE (2026-09-03). The canvas went 920 -> 890 and the graph now follows the
  content instead of being anchored to the canvas bottom, so the gap CT reported between the
  latency breakdown and the trace should be gone. Check all three modes and both a chosen and an
  unchosen clock source: the trace should sit just under the breakdown in every one of them, with
  any leftover room at the BOTTOM EDGE, and it must never overlap the Residual row.

- THE CLOCK INPUT IN LIVE (2026-09-03). Pick a source on the new "Clock in" row and confirm the
  CLOCK INPUT section fills: BPM, ms/clock, jitter, "vs host" in ppm, and RUNNING following the
  master's transport. Verified offline against synthetic clocks and against our own output through

- THE MEASUREMENT THE CLOCK INPUT EXISTS FOR: point Live's Sync at IAC Bus 1, point Clock in at the
  same port, and read Live's own clock jitter. Then set the plug-in's output to IAC instead, with
  Live's own sync OFF, and read ours the same way. Same code, same reference, both figures - this is
  the A/B the project has never been able to make honestly.
- Whether the "vs host" ppm figure is steady in a real host. Offline it wanders +/-26 ppm run to run
  against a fit standard error of about 3 ppm, which is suspected to be the usleep harness's pacing
  rather than the estimator. If Live shows the same wander, the estimator is at fault and the window
  or the gap ratio wants revisiting.
- MONITOR MODE AND THE CLOCK INPUT AT ONCE, which is now possible and has never been run: the audio

- The SETUP heading and the fifth control row, by eye. The canvas grew from 770 to 920 units for the

- The clock source surviving a saved set, including the case the destination side already handles:

- THE BACKGROUNDING FIX (2026-09-03). Reproduce what caused it: play in Live, watch Host block
  jitter settle, then bring another application to the front for half a minute and come back. The
  figure must stay where it was, and if the stall was long enough the row should read "(1 gap
  ignored)". Before this fix that scenario reported tens of milliseconds and never recovered.
- Whether Live announces the suspension at all - watch for setProcessing(0)/setActive(0) in
  /tmp/midisynctool.log around a backgrounding. If it does, ms_stats_gap() handles it and the gap
  count stays 0; if it does not, the 250 ms guard catches it and the count goes up. Either is
  correct, but which one fires says what Live actually does and is worth knowing.
- THE THREE-WAY MODE DROP-DOWN IN LIVE (2026-09-03), which replaced the two-state toggle on the

- The port row dimmed in monitor and the analyse row dimmed in clock-only: both must still be

- LOOP WRAP, which is the open question. The first capture had a 2-second heartbeat, far too coarse
  to show what Live does at a loop boundary. The build now logs "JUMP" the moment projectTimeMusic

  loop, let it go round several times, and read the JUMP lines - what matters is whether ppq goes
  BACKWARDS cleanly to the loop start, whether the sample position does the same, and whether the
  first block after the wrap is a normal-sized one.
- TEMPO CHANGE - not exercised in the first capture (CT: "I forgot to change the clock bpm"), so

- Audio passthrough: the plug-in copies input to output. Confirm a track with it inserted still

- Clock delivery jitter in LIVE. Settled offline against a real device callback: 0.033 ms RMS, and

- Whether MS_LOOKAHEAD_MS earns its place. The commit-margin telemetry now answers it from inside a
  host: if "late" stays 0 and the minimum margin never falls far below 10 ms, the lookahead is doing

- Transport in LIVE. Start/SPP/Continue/Stop are verified against the harness only. What matters in

- The 21.94 ms note round trip against a second reference. It is repeatable and the detector is

- Whether the resync threshold of 30 ms is right in Live: a tempo change or a loop should re-anchor
